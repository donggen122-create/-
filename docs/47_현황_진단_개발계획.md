## 2. 문제점 자세히

### A. 태블릿 렉 (1순위)
- 10/8 두 차례 최적화(거품 합성·축소 그림 캐시·정렬 거리 캐시 → 배포 전; 공간 격자 → 효과를 못 재서 `codex/tablet-lag-pass2` 브랜치에 보관). 거품 장면만 뚜렷이 좋아졌고, **군중 최악(4-3 적 160마리, CPU 6배 제한)은 9~10 FPS 그대로**.
- 남은 비용은 적 이동·충돌 계산(`updateEnemies`·`moveEnemy`·`resolveObstacles` — 적끼리·장애물과 매 프레임 거의 전부 비교). 9/30에 "적 수 ×1.6"으로 늘린 결정과 정면으로 부딪친다.
- **근본 문제는 측정이 없다는 것**: 판 결과에 FPS가 남지 않아 학생 태블릿 기종별로 얼마나 느린지, 몇 분부터 느린지 모른다. 지금까지의 모든 숫자는 PC 크롬 흉내다.

### B. 첫 로딩 21MB (2순위)
- 1장만 하는 학생도 4장 그림과 주제가까지 다 받는다. 교실 동시 접속에서 가장 먼저 터지는 곳이다.
- 캐시: HTML은 `no-cache`, 나머지는 Workers 기본값. 파일 이름에 버전이 없어 길게 캐시하기도 어렵다(바꾸면 옛 그림이 남을 수 있어서).

### C. 진행 절벽과 "왜 졌는지 모름" (3순위)
- 102명 중 1장 대왕을 넘은 학생이 27명. 2장 이후는 소수. 난이도 결정은 자동 조종 모의(3장 쉬움 45% 목표)에 기대고 있고, **실제 학생 기록으로 단계별 승률·탈락 단계를 본 적이 없다**(STATUS에 "학생 기록을 보고"가 세 번 미뤄져 있음).
- 결과 화면에 "무엇에 쓰러졌는지"가 없다 → 학생도 선생님도 밸런스팀도 원인을 모른다. 판 기록(`play_runs.result`)에도 쓰러진 까닭·시간이 없다.
- 1장을 못 넘는 학생에게 주는 길(훈련 안내·쉬움 권유·친구 카드)은 있지만 "다음에 뭘 하면 되는지"가 한 화면에 안 나온다.

### D. 이야기 부재 (4순위)
- 지식 카드·단계 한 줄·대왕 이름은 있지만 **인물이 말하는 장면이 하나도 없다**. 주제가·홍보 영상(호야가 거북에게 손을 내미는 이야기)과 게임이 서로 모른다.
- 스토리팀 3장 대본은 다듬은 초안까지 있다(`docs/44` 1절). 넣을 틀(말풍선 장면, 건너뛰기)이 없어 대기 중.

### E·F. 엔드 콘텐츠와 랭킹 (5순위)
- 4-5를 깬 학생은 같은 단계 반복(하루 2번만 보급권) 말고 할 것이 없다. 5장 구상안(`docs/40`)·학생 대왕 기획(`docs/44` 3절)은 있으나 결정 대기.
- 랭킹은 학생 투표(전교 개인 순위·가장 빠른 시간·학년별·매주·칭호)와 절충안(닉네임·1~10등+내 순위·주간 단계·명예의 전당)까지 나왔고 미구현. 서버에는 판마다 성공·시간이 남아 있어 만들 수 있다.

### G. 화면·사용성
- 출동 단추가 첫 화면 아래(위 2절). 공지가 매번 덮음. 소리 단추가 머리글 오른쪽 끝에만.
- 폰 375·태블릿 1024·세로 820 등 6크기는 도구로 점검했지만 **실제 기기 손가락 조작(가상 조이스틱·화면 끌기)의 느낌은 확인된 적이 없다**.
- 이름이 세 겹이다: 게임 데이터(LUMEN 챕터·광휘·봉화 등 옛 용어가 `content.data.js`에 그대로) ↔ 테마 이름 ↔ 활동지 이름. 학생 활동지가 게임과 다른 이름으로 나간 적이 있다(3장).

### H. 코드·운영 부채
- `main.js` 6,143줄 한 파일: 4장 행동(`sgT4Tick`), 3장 거품, 대왕 패턴, HUD, 결과가 섞여 있어 새 장을 넣을 때마다 커진다. `window.*` 전역 50개.
- 디버그 훅(`__debugGod` 등)은 localhost 가드가 있어 실서버에서는 안 통한다(확인). 하지만 **서버 정산은 "시간이 다 지났는지"만 검사**하고 `cleared`·처치 수·쓰레기 수·체력은 클라이언트가 보고한다 → 콘솔을 아는 학생이 5분 기다렸다 "성공"을 보낼 수 있다. 지금은 위험이 작지만 **랭킹을 넣으면 문제가 된다**.
- 가입이 인터넷 누구에게나 열려 있고(IP당 100회/시간), 아이디에 한글 실명이 들어갈 수 있다. 랭킹·닉네임 도입 전에 정리할 일.
- 배포 주체가 셋(Claude·Codex·사용자 휴대폰)이고 한 Worker를 쓴다. `check-live`로 막고 있지만 사람이 잊으면 서로 덮어쓴다. 이 PC의 `dist_web`은 동기화된 적이 없다(배포는 GitHub Actions라 문제는 아니지만 로컬 확인 절차와 어긋남).
- 문서: `CLAUDE.md`가 날짜별 로그로 커져 새 세션이 매번 26KB를 읽는다. `HANDOFF.md`는 3주 전 상태. "지금 규칙"과 "지난 일"이 섞여 있다.
- 소리: STATUS에 남은 `playSfx('attack')` 404 문제는 지금 코드에 그 호출이 없다(`attackFire`로 쓰고 있음) — 닫아도 된다.
- 단일 파일판(`LUMEN.html`)은 실서버와 다른 경로라 매번 깨진다(10/7에도). 쓰는 사람이 없으면 버리는 편이 싸다.

## 3. 개선안 (문제별)

### A. 렉 — "먼저 재고, 그다음 고친다"
1. **판 결과에 성능 요약 넣기**(작은 작업, 1KB 이하: 평균·하위 1% FPS, 긴 프레임 비율, 마지막 화질 단계, 기기 종류·화면 크기 구간, 버전). 서버는 값 범위만 검사해서 `play_runs.result`에 같이 저장. 개인 식별 정보 없음.
2. 관리 페이지에 **"기기별 FPS" 표**(기종 구간 × 단계 × 하위 1% FPS). 일주일이면 학교 태블릿의 실제 분포가 나온다.
3. 학생 태블릿 **2대를 직접 측정**(크롬 원격 디버깅 또는 위 기록) — 10분이면 된다. 이것 없이는 어떤 최적화도 효과를 말할 수 없다.
4. 그 자료로 결정: 보관된 공간 격자(`codex/tablet-lag-pass2`)를 넣을지, **느린 기기에서 적 수 상한을 두는 쪽**(이미 있는 화질 단계에 "적 동시 수 상한"을 한 단계 추가)이 더 확실한지. 화면이 느린 게 아니라 계산이 느리면 적 수가 답이다.
5. 장기: 적 이동·충돌을 공간 격자로, 그림은 스프라이트 시트로(그리기 호출 수 감소).

### B. 로딩 — "쓸 것만, 한 번만"
1. **장별 분할**: 적·바닥·효과 그림은 출동 단추를 누를 때 그 장 것만 받는다(지금은 전부 시작 때). 1장 학생은 4장 그림을 안 받는다.
2. **소리 지연**: 주제가·효과음은 첫 상호작용(시작하기) 뒤에 받는다. 3.7MB가 첫 화면에서 빠진다.
3. **그림 묶기·형식**: 장마다 스프라이트 시트 1~2장 + WebP(품질 유지, 10MB → 3MB 안팎 예상). 자르기 도구(`cut_theme*.py`)가 이미 있어 출력만 시트로 바꾸면 된다.
4. **캐시 규칙**: 파일 이름에 내용 해시(`main.abc123.js`)를 붙이고 `Cache-Control: max-age=1년`. 한 번 받은 기기는 다음 날 거의 0에 가깝다. (선택) 서비스 워커로 오프라인 캐시.
5. 목표: 첫 접속 **5MB 이하**, 두 번째 접속 **0.5MB 이하**.

### C. 진행 절벽 — "자료를 보이게"
1. 관리 페이지 **단계별 그래프**: 단계마다 도전 수·성공률·마지막으로 멈춘 학생 수(`play_runs`로 바로 계산 가능). 난이도 결정의 근거가 된다.
2. 결과 화면에 **"쓰러진 까닭"**(어떤 적/대왕 기술, 몇 분에) + 판 기록에 저장. 밸런스팀 과제 5번(대왕 기술 조사)과 바로 이어진다.
3. 실패 뒤 **다음 할 일 한 칸**: "훈련 공격력 2단계 올리기(코인 OK)" / "쉬움으로 한 번" / "친구 꼬북이 끼기" 중 하나를 자동 추천.
4. 1장 학생 기록을 보고 1-3~1-5 배율을 다시 본다(지금은 모의 승률만).

### D. 이야기 — "말풍선 장면 하나를 만들면 모든 장에 쓴다"
1. **대화 장면 틀** 하나: 얼굴 그림 + 이름 + 한 줄, 탭/클릭으로 넘김, 건너뛰기 단추, 한 번 본 장면은 다시 안 나옴. 장 시작·대왕 등장·장 끝 3곳.
2. 스토리팀 대본으로 3장부터(다듬은 초안 `docs/44`), 1·2장 대본이 오면 1~3장 한 번에. 필요한 그림: 호야·민지·친구 4·대왕 4의 얼굴, 개굴이.
3. 홍보 영상의 결정적 장면(쓰러진 친구에게 손을 내밈)을 **게임의 어느 장 끝 장면**으로 둘지 정하면 영상·노래·게임이 한 이야기가 된다.

### E·F. 엔드 콘텐츠·랭킹
1. **랭킹(절충안)**: 닉네임(선생님 승인·금칙어) · 1~10등 + 내 순위 · 학년별 · 매주 단계 하나 · 명예의 전당(대왕 정화한 모두) · 칭호. 서버 기록으로 가능. **단, H-2(결과 검증)를 먼저**.
2. **반 협동 목표**(학급 정화 수 합산 → 반 전체 보상): 실시간 연결 없이도 되고 학생이 걱정한 "순위 낮은 아이의 포기"를 보완.
3. **5장 플라스틱 바다**: `docs/40` 기본안 + 기획팀 대왕(문어왕에 빨대 삼지창·플라스틱 갑옷). 단계 목표 A(산호 되살리기) 추천. 그림 11장 → `cut_theme5.py` → CH21~25.
4. **6장 뜨거운 지구 + 엔딩**: 탄소 대왕 정화 → 마을 전경이 맑아지는 엔딩 장면(홍보 영상 끝과 맞춤). 6장은 "지금까지 모든 장의 적이 섞여 나오는 총정리" 구성이면 새 몬스터가 적어도 된다.

### G. 화면
1. 로비 모험 탭: **출동 카드를 단계 지도 위로** 올리거나 출동 단추를 화면 아래에 고정(스크롤해도 보이게). 6크기 점검 도구에 "출동 단추가 첫 화면에 보이는가" 항목 추가.
2. 공지는 로그인 뒤 **한 번만**(이미 '다시 보지 않기' 있음 → 기본을 1회로).
3. 실제 기기 손 조작 점검 1회(태블릿·폰에서 가상 조이스틱 크기·끌기 반응). 결과를 `docs/31`에 보탬.
4. 옛 LUMEN 용어 정리(`content.data.js`의 챕터 이름 등은 화면에 안 보이지만 31단계 이후에 새어 나올 수 있음).

### H. 코드·운영
1. **서버 결과 검증 강화**(랭킹 전 필수): 처치 수·쓰레기 수·시간의 상한과 비율 검사, 대왕 단계는 `bossSeconds` 필수, 같은 판 두 번 정산 방지(있음). 이상 판은 기록만 하고 보상은 보류 → 관리 페이지에 표시.
2. **가입 코드**(선택): 학급 코드를 넣어야 가입되게 → 외부 가입 차단, 반·번호를 선생님이 묶어 볼 수 있음(관리 페이지 "학급별" 요구와 연결).
3. **`main.js` 분할**: 엔진(루프·입력·그리기) / 적 행동(장별 `t1~t4` 파일) / 대왕 / HUD·결과. 규칙은 그대로, 파일만 나눈다. 분할 뒤 같은 시드 재생 검사(이미 있는 `replay`)로 결과 동일 확인.
4. **검사 자동화**: GitHub Actions 배포 전에 브라우저 스모크(가입 → 1-1 출동 → 결과)와 6크기 점검을 자동으로. 지금은 사람이 돌린다.
5. **문서 정리**: `CLAUDE.md`는 "지금 규칙"만 2~3KB로 줄이고 날짜 로그는 `game/STATUS.md`로 이동, `HANDOFF.md`는 현재 구조로 다시 씀. 새 세션 비용이 줄고 실수가 준다.
6. 단일 파일판은 쓰는 사람이 없으면 중단(매번 수리 비용).

## 5. 선생님이 정해 주실 것
1. 0단계(실태 파악)를 먼저 할지 — 추천.
2. 로딩: 장별 분할·소리 지연·그림 시트까지(기본) / 서비스 워커까지(추가).
3. 이야기 장면: 가(단계 한 줄만 대본 말투로) / 나(말풍선 장면, 추천).
4. 랭킹: 절충안으로 갈지, 공개 범위(1~10등 + 내 순위 추천), 닉네임 승인 방식.
5. 가입 코드(학급 코드) 도입 여부.
6. 5장 단계 목표 A(산호 되살리기, 추천) / B(아기 거북 호위), 대왕은 기획팀 안 + `docs/40` 합친 안으로 갈지.
7. 단일 파일판을 계속 만들지.
