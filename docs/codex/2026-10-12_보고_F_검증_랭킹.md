## ① 성공 조건과 순위 기준

`guardian.js`의 `/play/finish`는 성공 시 실경과 시간도 `elapsed+3 >= duration`이어야 하고, 정산 입력도 `seconds+3 >= duration`이어야 합니다. 기존대로 정산 seconds는 360 이하, 실경과 시간+2 이하로 제한합니다. 첫 CH01/CH02 180초, 일반 단계 300초, 대왕 출현까지 240초라서 가장 빠른 성공 시간은 일반 단계에서 사실상 고정입니다. 순위 기준으로 쓰지 않고 지시대로 이번 주 단계 **한 판 최고 처치 수 → 목표물 수 → 먼저 정산한 시각**을 사용합니다.

처치 수는 기존 클라이언트의 판 요약 `__debugOutcome()`에서 `cloud.js`가 요청에 추가합니다. `main.js` 전투·피해·결과 로직과 `completeRun()`은 바꾸지 않았습니다. 같은 판의 전송 재시도·새로고침에는 sessionStorage에 보관한 처치 수를 다시 첨부합니다. 옛 정산 기록에는 처치 수가 없으므로 주간 순위에는 넣지 않고 대왕 명예의 전당에는 사용할 수 있습니다.

## ⑤ 실제 D1 마이그레이션 방법 (실행하지 않음)

Claude/선생님이 배포 시 **새 서버의 첫 요청 전에**, 기존 DB에 새 열이 아직 없는 것을 확인하고 한 번 적용할 수 있습니다:

```powershell
npx wrangler d1 execute seoho-pangpang-db --remote --file=server/migrations/2026-10-12_ranking.sql
```

wrangler 설정 검색 경로가 달라지면 저장소 루트에서 `--config server/wrangler.toml`을 함께 지정합니다. 이 작업에서는 명령을 실행하지 않았습니다.

실행을 생략해도 첫 Guardian/랭킹/관리 요청에서 기존 표 생성 직후 `PRAGMA table_info(users/play_runs)`로 빠진 열을 확인하고 ADD COLUMN·settings·색인을 자동 적용합니다. DB별 promise로 isolate 내 1회이며 오류 시 다음 요청에서 다시 시도합니다. 구형 열 없는 DB와 반복 적용을 로컬 SQLite로 검증했습니다. `schema.sql`도 새 DB의 열·색인을 포함합니다.

**자동 적용이 이미 끝난 DB에 SQL 파일을 다시 실행하지 마세요.** SQLite ALTER ADD COLUMN은 이 파일에서 재실행 가능하지 않습니다. 그 경우 PRAGMA 확인 후 빠진 ALTER만 실행하거나 서버 자동 적용으로 충분합니다. 자동 적용 때문에 수동 실행은 필수가 아니지만 실제 D1 권한·잠금·운영 적용은 이 작업에서 확인하지 않았습니다. D1 batch의 트랜잭션 동작은 [공식 D1 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/)를 참고했습니다.
