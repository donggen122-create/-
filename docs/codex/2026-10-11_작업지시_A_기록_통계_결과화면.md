## 0. 지킬 것
- 이 폴더는 git worktree, 브랜치 **`codex/2026-10-11-A`**. 여기서만 작업하고 여기서만 커밋한다(작게 나눠서). **push 금지, 배포 금지, `main`·`seoho-game` 브랜치 건드리기 금지.** Claude가 검토한 뒤 합친다.
- **다른 Codex 세션(B)이 옆 폴더 `../seoho-codex-B`에서 같은 시각에 로딩·로비 화면을 고치고 있다.** 충돌을 피하기 위해 파일을 나눈다:
  - **A(너)가 고쳐도 되는 것**: `server/src/*`, `game/admin/*`, `game/src/main.js`의 **판 끝(`sgEnd`)·결과 화면·주인공 피해 처리(`player.hp -= d` 근처)·성능 표본 수집 부분만**, `game/src/rework-core.js`에 **읽기 전용 도우미 함수 추가만**(규칙·수치 변경 금지), `tests/*`, `game/tools/qa/*`, `HANDOFF.md`, `docs/codex/*`, `game/STATUS.md` 맨 위.
  - **손대지 말 것**: `game/src/assets.js`, `game/index.html`, `game/src/ui2-art.js`, `game/src/rework-ui.js`, `game/src/ui-v2.css`·`rework.css`, `main.js`의 그림 불러오기·공지(`sgChapter4Notice`)·적 생성(spawn) 부분, `docs/47`, `CLAUDE.md`, `홍보영상/`.
- 격리 서버는 **포트 8798**: `PORT=8798 node game/tools/qa/node-server.mjs` (B가 8797을 쓴다). 브라우저 점검 도구에는 `--url http://localhost:8798/...`.

- 새 표(테이블)는 만들지 않는다. 기록은 기존 `play_runs.result` JSON 안에 넣는다.

## 1. 판 결과 성능 요약 기록 (0단계 ②)
목표: 학생이 실제 기기로 한 판을 하면 그 판의 성능이 서버에 남고, 관리 페이지에서 기기 종류별로 보인다.
1. 클라이언트(`main.js`): 판 동안 프레임 간격을 모아(QA 전용 `qaPerf`를 참고하되 **항상 켜져 있는 가벼운 수집기**를 따로 둔다 — 배열을 무한히 쌓지 말고 누적 합·히스토그램 같은 고정 크기로) 판이 끝날 때 `sgEnd`가 보내는 결과에 `perf`를 붙인다:
   `{v:<게임 버전 문자열>, fps:<평균>, p1:<하위 1% 프레임 간격을 FPS로>, long33:<33ms 초과 비율 0~1>, long50:<50ms 초과 비율>, q:<마지막 화질 단계 index>, ratio:<마지막 해상도 배율>, qmax:<판 중 가장 낮았던 화질 단계>, dev:'tablet'|'phone'|'pc', w:<화면 가로 구간 320/375/768/1024/1280/1600 중 가장 가까운 아래값>, h:<세로 구간>, dpr:<소수 둘째 자리>, sec:<판 길이 초>}`. 600바이트 이하. `dev`는 UA·`pointer: coarse`·화면 크기로 판정하되 UA 문자열은 저장하지 않는다.
2. 서버(`server/src/guardian.js` `/play/finish`): `b.perf`가 있으면 **모든 값을 검사**(유한수·범위·허용 목록·문자열 길이·전체 1KB 이하)하고 통과한 것만 `event.perf`로 `play_runs.result`에 저장한다. 없거나 이상하면 그 판은 perf 없이 저장(판 자체를 거부하지 않는다). 검사 함수는 단위 검사로 덮는다.
3. 관리 페이지(`game/admin/index.html`): 새 묶음 **「기기별 성능」** — 최근 N일(기본 30, 바꿀 수 있게) 판 기록의 perf를 `dev × 화면 구간`으로 묶어 판 수·평균 FPS 중앙값·하위 1% FPS 중앙값·긴 프레임(50ms) 비율 중앙값·마지막 화질 단계 분포를 표로. 단계별(4-3 등)로도 볼 수 있게 열 하나. 서버 쪽 집계는 2절의 `stage-stats`에 같이 넣어도 된다. 시험 계정(`TEST_ACCOUNT_RE`)은 집계에서 뺀다.

## 2. 관리 페이지 「단계별 현황」 (0단계 ①)
목표: 선생님이 "어느 단계에서 몇 명이 멈춰 있고, 승률이 얼마고, 왜 지는지"를 한 화면에서 본다.
1. 서버: `GET /api/admin/stage-stats?days=30` (선생님 역할도 읽을 수 있게 — `TEACHER_BLOCKED`에 넣지 않는다). 단계마다: 도전 수, 성공 수, 승률, 도전한 학생 수(중복 제거), **여기서 멈춘 학생 수**(= 그 학생의 최고 정화 단계가 바로 앞 단계이고 이 단계 기록이 1판 이상), 난이도별 도전·성공(판 기록에 난이도가 없으면 **지금부터 남기도록** `/play/start`의 `result.loadout`에 난이도를 추가하고, 없는 옛 기록은 "모름"으로), 자주 쓰러진 까닭 상위 3(3절), 성능 중앙값(1절). 시험 계정 제외. 학생 아이디는 응답에 넣지 않는다.
2. 관리 페이지: 표 + CSS 막대(외부 차트 라이브러리 금지)로 **단계 20개를 한눈에**(승률 막대, 멈춘 학생 수가 많은 단계는 눈에 띄게). 기간 고르기(7·30·전체).
3. 단위 검사: 가짜 판 기록 몇 개로 집계 결과(승률·멈춘 학생·시험 계정 제외)를 검사.

## 3. 결과 화면 「쓰러진 까닭」 + 다음 할 일 (1단계 ④)
1. `main.js` 주인공 피해 처리에서 **마지막으로 맞은 것**을 기록: `{id, kind:'enemy'|'boss'|'hazard'|'shot', at:<판 시간 초>}` — id는 적 정의 id(예 `T4_SAW`), 대왕 기술 이름(`BOSS_PATTERNS_*`의 키), 오염 구역(`zone`)·불길 같은 위험 이름. 쓰러지면 그것이 `cause`.
2. 실패 결과 화면에 한 줄: "쓰러진 까닭: 톱니몬의 회전 (3분 12초)" — 화면 이름은 적·기술의 **한글 표시 이름**(themes.js·boss-patterns.js에 있는 이름). 성공한 판에는 안 보인다. UI 1·UI 2 둘 다에서 한 줄이 넘치지 않게(폰 375 포함).
3. 결과에 `cause:{id,kind,at}`를 붙여 보내고, 서버는 id를 `^[A-Za-z0-9_:-]{1,40}$`·kind 허용 목록·at 범위로 검사해 `event.cause`로 저장.
4. **다음 할 일 한 줄**(실패한 판에만): 지금 결과 화면에 이미 있는 "다음 할 일" 줄이 있으면 그것을 **까닭에 따라** 고른다 — 대왕 기술에 쓰러짐 → "대왕 기술은 빨간 표시 밖으로 피해요", 코인이 훈련비 이상이고 공격력/체력 훈련이 낮음 → "훈련 ○○ 올리기(코인 OK)", 어려움·보통에서 졌으면 → "쉬움으로 한 번", 친구가 없으면 → "친구 꼬북이 끼기". 규칙은 `rework-core.js`에 **읽기 전용 함수**로 두고 검사로 덮는다. 서버 규칙은 바꾸지 않는다.
